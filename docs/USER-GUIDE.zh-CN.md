# 诊断流程用户手册

[English](USER-GUIDE.md) · [项目说明](../README.zh-CN.md)

本手册说明如何把现有 Python 工程接入平台，再用流程图调用其中的函数或对象方法。按第 1～6 节操作，可以完成一次真实执行；第 7 节提供另一个完整 Python 工程，第 8 节以后说明分支规则、人工处理、文件保存和其他使用方式。

第 1～6 节使用仓库自带的设备电压示例。它会采集一个 Python 对象，判断电压是否偏低，再恢复并复核设备。示例中的设备操作均为模拟。跑通后，将示例目录、模块和类替换为自己的工程即可。

## 1. 先明确各部分负责什么

画布决定节点之间的依赖和执行路径。节点绑定的 Python 接口负责实际业务：采集、计算、访问设备、修改对象状态或执行处置。Flowable 根据节点结果推进流程，并保存执行进度、等待状态和历史。

真实运行需要以下四个程序配合，启动后都应保持运行：

| 程序                      | 负责的工作                                      | 启动时机                     |
| ------------------------- | ----------------------------------------------- | ---------------------------- |
| 前端页面                  | 编辑流程、配置接口、显示结果                    | 开始使用平台时               |
| 本机后端                  | 登记 Python 工程、提供调试和执行服务            | 登记工程前                   |
| Flowable 服务             | 调度流程、处理分支和人工等待                    | 启动整张流程前               |
| Python worker（工作进程） | 接收 Flowable 任务，在业务工程环境中调用 Python | 导出执行包之后、启动流程之前 |

**Python 项目**用于登记和调试接口；**Flowable 执行**用于运行整张流程。**开启结构模拟**只播放画布上的令牌动画，不会执行 Python，也不能证明接口和排查规则正确。

## 2. 准备环境并打开平台

### 2.1 首次准备

本地源码运行需要 Node.js 22、pnpm、Python 3.9+、Java 21 和 Maven 3.9。业务工程另外需要的 Python 包，应安装在该工程自己的解释器环境中。

先在本仓库根目录准备前端依赖、worker 环境和 Java 服务：

```powershell
pnpm install
python -m venv backend/.local/venv
backend/.local/venv/Scripts/python.exe -m pip install -r backend/requirements-flowable.txt
mvn -f flowable-runtime/pom.xml package
```

已有这些环境时直接复用，无需重复创建。`backend/.local/venv`供 worker 使用，安装官方 Flowable 客户端；它可以与业务工程的虚拟环境不同。worker 会读取工程登记信息，用所登记的解释器运行实际业务。

### 2.2 启动编辑页面和本机后端

打开两个终端，工作目录都设为本仓库根目录。

第一个终端启动后端：

```powershell
python backend/server.py
```

第二个终端启动前端：

```powershell
pnpm dev
```

在浏览器打开 Vite 输出的地址。默认情况下，前端把 `/api` 请求转发到 `127.0.0.1:8765`。后端默认接受前端的 5173、5174 端口；若实际使用其他端口，启动后端时用 `--origin` 指定页面来源，例如：

```powershell
python backend/server.py --origin http://localhost:5175
```

也可以先运行 `pnpm build-only`，再通过后端打开 `http://127.0.0.1:8765/vue-bpmn-designer/`，此时无需保持 Vite 运行。

### 2.3 启动 Flowable

另开一个终端，从本仓库根目录进入 Java 服务目录并启动：

```powershell
cd flowable-runtime
java -jar target/diagnostic-flowable-1.0.0.jar
```

默认服务地址为 `http://127.0.0.1:8080`，本地示例账号为 `diagnostic`，密码为 `local-demo`。如果修改地址或账号，后端与 worker 必须使用一致的 `FLOWABLE_URL`、`FLOWABLE_USER`、`FLOWABLE_PASSWORD` 环境变量。

此时可以登记工程和编辑流程。worker 需要使用稍后导出的 `bindings.json`，在第 6 节启动。

## 3. 接入 Python 工程，先验证接口能正常调用

### 3.1 登记设备示例

点击顶栏 **Python 项目**，填写：

| 界面字段             | 本例填写值                         | 含义                                                                     |
| -------------------- | ---------------------------------- | ------------------------------------------------------------------------ |
| 项目名称（可选）     | 设备电压示例                       | 便于在列表中辨认                                                         |
| 项目目录             | `backend/examples/session_project` | 业务工程根目录；相对路径以本仓库根目录为起点                             |
| 入口模块             | `device_session`                   | Python 可导入的模块名，不是文件路径                                      |
| 会话类或工厂（可选） | `Device`                           | 本例要调用的类                                                           |
| Python 解释器        | 可留空                             | 留空使用后端解释器；接入自己的工程时填写其虚拟环境中的 `python.exe` 路径 |

点击 **接入项目**。接口列表应出现 `ready`、`collect`、`is_low`、`restore`、`verify` 和 `restore_and_verify`。

登记不会复制或修改外部工程。界面上的目录是**运行后端那台电脑上的目录**。工程使用 `src/` 布局也可以；运行时会加入工程的 `src/`、根目录和父目录作为导入搜索路径，并以工程根目录作为工作目录。

### 3.2 连续调用，确认对象状态能保留

在同一个项目中依次操作：

1. 选择 `collect`，初始化参数先留空，点击 **调用 Python 接口**。它采用默认设备号 `M01` 和阈值 `24`，返回电压为 `22.6` 的 `Reading` 对象。
2. 选择 `restore` 并调用。它修改当前设备实例的恢复状态，返回 `None`；界面显示为 `null`，表示正常的无返回值。
3. 选择 `verify` 并调用。它在同一个设备实例上重新采集，得到恢复后的电压 `24.5`，判断通过，结果为 `true`。
4. 点击 **重置调试会话**，再调用 `verify`。新实例尚未恢复，结果应为 `false`。

这四步确认了：接口可以导入、普通与异步方法都能运行、连续调用能使用同一个实例、重置后状态不会沿用。

表单依据函数签名生成。数字、布尔值、`null`、数组和对象会自动识别，其他输入按文本传入；输入空字符串时填写 `""`。可选字段留空就保留 Python 默认值。`self`和实例内部属性不需要人工填写。可变参数 `*args`、`**kwargs` 位于高级输入中，普通调用无需使用它们。

本例不在单接口调试中手工构造 `is_low` 所需的 `Reading` 对象；下一节由流程传递这个对象。界面显示的对象文字不能作为原生对象复制回输入框。

调试只执行所选接口，不会运行整张流程，也不与正式流程共享设备实例。切换项目、重新读取接口或移除登记会关闭对应调试会话。单次调用默认超时 120 秒，可用 `python backend/server.py --timeout 600` 调整；超时会关闭该会话。

### 3.3 换成自己的工程时怎样填写

例如文件位于 `D:/equipment/diagnostics/machine/api.py`，其中定义或导出了 `Device`：项目目录填 `D:/equipment/diagnostics`，入口模块填 `machine.api`，会话类或工厂填 `Device`，解释器填该工程实际使用的 `python.exe`。

入口有以下三种用法：

| 工程已有的接口形式                        | 会话类或工厂字段       | 平台调用方式                                 |
| ----------------------------------------- | ---------------------- | -------------------------------------------- |
| 模块中的普通函数                          | 留空                   | 直接调用模块公开函数                         |
| 现有类，例如 `Device`                     | 填类名                 | 每次排查创建实例，节点调用其公开方法         |
| 返回业务对象的工厂，例如 `create_session` | 填工厂函数名或公开路径 | 每次排查调用工厂一次，随后调用返回对象的方法 |

普通函数默认展示入口模块自身定义的公开函数；若要展示其他模块重导出的函数，在入口中用 `__all__` 列出它们。类的实例方法会自动去掉 `self`。

登记类时只检查方法，不创建实例；构造函数有必填参数也可以登记。工厂有返回类的类型注解时，同样可以直接发现方法，例如示例中的 `create_session(...) -> Device`。没有返回类注解的工厂会在登记时用默认参数临时创建一个对象来发现接口；若它有必填参数，需要先补上返回类注解。

代码或签名修改后，点击 **重新读取接口**。登记信息保存在 `backend/.local/projects.json`；**移除接入（保留文件）**只删除登记，不删除业务工程。

## 4. 导入示例流程，理解每个节点调用什么

点击 **导入项目目录**，选择本仓库的 `backend/examples/session_project` 文件夹。该目录已包含 `workflow.json` 和参考文件，导入后会自动生成布局。导入会替换当前画布，已有工作应先导出保存。

示例只有一条恢复思路：

```text
开始
  ↓
入口排查 ready ──是──→ 采集动作 collect
                          ↓
                    电压排查 is_low
                          │ 是
                          ↓
                         结论
                          ↓
                  处置 restore_and_verify
                          ↓
                        问题解决
```

选中节点，可以在右侧查看以下绑定。所有业务节点使用模块 `device_session`、会话类 `Device`；工作主题留空即可。

| 节点标识     | 节点类型 | 接口                 | 运行时发生什么                                   |
| ------------ | -------- | -------------------- | ------------------------------------------------ |
| `Ready`      | 排查     | `ready`              | 首次使用时创建 `Device`，返回 `True` 后进入采集  |
| `reading`    | 排查动作 | `collect`            | 返回原生 `Reading` 对象，保存为该节点的结果      |
| `Check`      | 排查     | `is_low`             | 接收上一步的原对象，判断电压是否偏低             |
| `Conclusion` | 结论     | 不绑定               | 记录电压偏低这一结论                             |
| `Repair`     | 处置措施 | `restore_and_verify` | 在同一实例上恢复，再异步复核；复核失败则抛出异常 |
| `Solved`     | 问题解决 | 不绑定               | 表示这条恢复思路已完成                           |

排查节点在 **执行与人工判断** 中选择接口，动作和处置节点在 **接口绑定** 中选择接口。只记录文字的结论无需接口，问题解决和上升节点也不绑定业务函数。不要把 `Device.collect()` 这样的调用表达式填入函数名称；选择 `collect` 即可。

自行画图时，按同一张表创建节点和绑定。采集节点的 **常规 → 标识** 必须是 `reading`，因为示例判断方法的参数名就是 `reading`。名称可以自行填写，或留空由详细内容生成。

这个例子只实现“电压偏低后尝试恢复”。两个排查节点都只配置“是”出口；如果判断为否且没有匹配出口，就记录为该思路失败。它没有把“电压正常”设计成另一条成功路径。需要这种路径时，应另外补上符合连接规则的节点。

## 5. 理解参数和对象怎样传递

本例的关键调用关系相当于：

```python
device = Device(device_id='M01', threshold=24)
device.ready()
reading = device.collect()
device.is_low(reading)
# 判断成立后，在同一实例上调用异步的 restore_and_verify。
```

节点选择相同的模块与类／工厂时，会在同一次排查中复用同一个实例。对象属性由原来的 Python 方法维护，不需要把 `latest`、`attempts`、`recovered` 等内部状态重新配置成平台参数。另一次排查使用自己的进程和实例。

对于确实声明在函数签名中的输入，平台按下面的顺序寻找数据：

1. 同名启动变量，或以节点标识保存的完整结果。例如参数 `reading` 对应采集节点 `reading` 的原始结果。
2. 已执行上游节点返回的字典中，唯一的同名字段。例如结果含 `voltage`，后续方法也声明 `voltage` 参数。
3. Python 函数本身的默认值。

旧流程若保存了显式参数映射，仍会优先使用它。新流程无需在节点中编写参数代码或表达式。数据不足时由 Python 报告缺参；出现两个同名候选字段时，平台报告来源不唯一，不会替用户猜测。

原始对象保留在该工程的 Python 会话中。Flowable 和界面保存的是便于查看的结果；不能直接转成 JSON 的对象，会显示其类型和文字表示。这些文字不会替代原对象传给后续方法。不同工程的子进程之间不能直接传递原生对象引用。

判断节点必须给出明确结果：`True`、`False`、`yes`、`no`、`是`、`否`，或含 `next` 字段的字典，例如 `{'next': 'yes', 'voltage': 22.6}`。英文判断忽略大小写；兼容的旧连线 ID 返回值会选择该连线所属的整个分组。普通数字或任意对象的真假性不会自动作为分支判断。

动作可以没有输入，也可以返回 `None`；只有需要选择后续分支的排查才必须给出判断结果。`async def` 方法可以直接绑定。

## 6. 导出执行包并运行整张流程

### 6.1 导出执行包

点击 **Flowable 执行 → 导出执行包**，将下载的压缩包解压到一个固定目录，例如 `D:/exports/device-session`。包内三个文件各有用途：

| 文件                  | 用途                         |
| --------------------- | ---------------------------- |
| `source.bpmn`         | 当前流程的完整编辑快照       |
| `workflow.bpmn20.xml` | 交给 Flowable 部署的执行定义 |
| `bindings.json`       | worker 使用的节点接口绑定    |

后面的 worker 命令需要指向解压后的 `bindings.json`。继续编辑时使用 `source.bpmn`，不要把编译后的执行定义当成原图。

### 6.2 启动 worker

再开一个终端，工作目录设为本仓库根目录，运行：

```powershell
backend/.local/venv/Scripts/python.exe backend/flowable_worker.py D:/exports/device-session/bindings.json
```

看到 `Subscribed:` 和任务主题后，说明 worker 已开始监听。默认读取 `backend/.local/projects.json`，用其中登记的解释器和工作目录执行业务；不要求把业务依赖重复安装进 worker 环境。

同一 Flowable 服务的相同执行包只启动一个 worker。它可以同时管理多次排查，每次排查使用独立的业务进程。同机重复启动会明确拒绝；不同机器之间也须保持单个协调器，本机锁不能跨机器协调。

### 6.3 填写启动输入并启动

回到 **Flowable 执行**。启动表单会读取已登记类或工厂的初始化参数。本例可填写 `device_id` 为 `M01`、`threshold` 为 `24`；也可全部留空，采用 `Device` 的默认值。

其他启动数据通过 **添加启动输入**填写名称和值。普通方法的参数可能来自上游结果，因此不会全部被当成启动必填项。若初始化所需数据由前面的节点产生，也可以留待上游提供。同名启动变量在整张流程中共享；多个工厂若有同名参数，填写一个值会同时影响它们，留空则各自采用默认值。

点击 **部署并启动**。平台部署当前画布并创建流程实例；此前单接口调试中的恢复状态不会带入本次流程。

需要兼容原有输入方式时，可展开 **高级：初始变量 JSON**并开启 **使用 JSON 代替表单**。此时只使用该 JSON 对象，表单不参与合并；默认内容为 `{}`。使用内置诊断示例时，可直接从下拉框选择示例场景。

### 6.4 确认运行结果

点击 **刷新执行结果**。默认参数下，本例应依次完成 `Ready → reading → Check → Conclusion → Repair → Solved`，最终显示流程已结束。

在 **执行详情** 中可以查看节点结果和历史。采集结果是 `Reading` 的展示信息；处置返回 `null` 是正常的无返回值。恢复复核若不通过，例如阈值设置为 `30`，`Repair` 会报错，流程不会到达问题解决。

任务报错后刷新结果，展开失败详情查看原始 Python 异常堆栈；其中保留业务文件、调用位置和异常信息。worker 终端中的输出可用于补充排查。结果字典含 `chartSvg` 字符串时，界面可以展示该图表；仅返回本机文件路径不会自动显示图片。

## 7. 第二个完整示例：冷却系统 Python 工程

前面的电压示例是一条恢复路径。这个示例提供一个独立的 Python 工程，演示两种互不依赖的排查手段如何并列执行、怎样传递原生对象，以及成功、思路失败和任务报错分别会出现什么结果。

### 7.1 先了解工程中的内容

工程位于 `backend/examples/cooling_project`，只使用 Python 标准库，不依赖平台才能运行。其中所有设备操作均为模拟。

| 文件                           | 负责什么                                         |
| ------------------------------ | ------------------------------------------------ |
| `src/cooling_lab/api.py`       | 对平台公开 `CoolingSession`                      |
| `src/cooling_lab/session.py`   | 采集、判断、处置与复核的业务接口                 |
| `src/cooling_lab/simulator.py` | 模拟设备，维护滤网、风机和温度状态，保护并行访问 |
| `src/cooling_lab/models.py`    | 原生 `Measurement` 采集对象和阈值类型            |
| `src/cooling_lab/charts.py`    | 生成处置前后的 SVG 温度图                        |
| `assets/limits.csv`            | Python 实际读取的阈值，同时作为节点参考文件      |
| `assets/scenarios.json`        | 五种模拟场景的初始状态                           |
| `run_demo.py`                  | 不通过平台，直接运行同一套业务接口               |
| `workflow.json`                | 已绑定这些接口的并行流程；资源均使用相对路径     |

### 7.2 先独立运行，再接入平台

从仓库根目录运行：

```powershell
python backend/examples/cooling_project/run_demo.py --scenario fan
```

默认设备号为 `COOL-01`。这个场景的风机转速过低，重启后温度从 85 C 降至 42 C；终端会输出处置结果。需要保存温度图时，加上输出路径：

```powershell
python backend/examples/cooling_project/run_demo.py --scenario fan --report backend/examples/cooling_project/output/fan.svg
```

确认业务工程自身能运行后，再使用准备命令把它接入平台：

```powershell
pnpm exec node scripts/prepare-cooling-example.mjs
```

这个命令会依次完成三件事：为示例创建独立的 `.venv`；把工程登记到 **Python 项目**；生成已绑定接口的执行包。它不会修改旧示例、当前画布或已有流程。若默认 `python` 不可用，在命令后增加 `--python`，填写现有解释器的路径。

后端运行时通过其 API 登记，未运行时保存到默认登记文件，下次启动后端即可看到。命令输出工程 ID、实际解释器路径和执行包目录；登记信息如下：

| 配置       | 值                                            |
| ---------- | --------------------------------------------- |
| 项目名称   | `Cooling Lab / 冷却系统示例`                  |
| 项目目录   | 本仓库下的 `backend/examples/cooling_project` |
| 入口模块   | `cooling_lab.api`                             |
| 会话类     | `CoolingSession`                              |
| 业务解释器 | 准备命令输出的 `.venv` 完整路径               |

打开 **Python 项目**，点击 **刷新项目列表**，选中这个工程，应看到 11 个公开接口。先选择 `summary` 并用默认参数调用，温度应为 85 C；在同一调试会话调用 `restart_fan`，再调用 `summary`，温度应为 42 C，处置记录为 `restart_fan`。这样可以先确认类实例和异步接口的接入，再运行整张图。

### 7.3 导入流程并启动

在页面点击 **导入项目目录**，选择 `backend/examples/cooling_project`。导入前先保存当前画布。流程的主体关系是：

```text
初始超温排查
  ├─ 是 → 风路采集 air_sample → 滤网判断 → 结论 → 清理 → 复采报告 ─┐
  ├─ 是 → 风机采集 fan_sample → 转速判断 → 结论 → 重启 → 复采报告 ─┼→ 问题解决
  └─ 否 → 正常结论 → 正常报告 ───────────────────────────────────┘
```

风路采集和风机采集互不依赖，都接在前置排查的“是”出口。每种判断则依赖自己的采集，不能绕过采集直接执行。

| 节点标识                      | 调用的方法                      | 关键关系                                   |
| ----------------------------- | ------------------------------- | ------------------------------------------ |
| `Overheat`                    | `is_overheated`                 | “是”启动两条思路，“否”走正常记录           |
| `air_sample`                  | `collect_air`                   | 返回原生 `Measurement`                     |
| `FilterCheck`                 | `filter_is_blocked`             | `air_sample` 参数接收上一步的原始对象      |
| `CleanFilter`、`FilterReport` | `clean_filter`、`report_filter` | 先完成清理，再复采并生成报告               |
| `fan_sample`                  | `collect_fan`                   | 返回另一条思路自己的原生对象               |
| `FanCheck`                    | `fan_is_faulty`                 | `fan_sample` 参数接收对应采集对象          |
| `RestartFan`、`FanReport`     | `restart_fan`、`report_fan`     | 异步重启完成后才复采，不把 `None` 当成失败 |
| `NormalReport`                | `report_healthy`                | 正常设备只记录，不执行维修                 |

这些节点均已绑定模块 `cooling_lab.api` 和类 `CoolingSession`。处置和报告继续使用本次流程的同一个设备实例，不用再次填写设备内部状态。

准备命令已经生成执行包，无需为第一次运行再导出一次。保持第 2 节的后端、页面和 Java 服务运行，在仓库根目录启动：

```powershell
backend/.local/venv/Scripts/python.exe backend/flowable_worker.py backend/.local/cooling-example-parallel/bindings.json
```

回到 **Flowable 执行**，点击 **重新读取启动输入**。`scenario` 填 `fan`，`device_id` 填 `COOL-01`，或都留空采用默认值；然后点击 **部署并启动**。这会创建新的业务实例，不沿用刚才调试过的设备状态。

刷新执行结果后，应看到滤网思路因判断不成立而结束，风机思路完成重启，整体到达问题解决。报告中的温度图应从 85 C 降到 42 C。另一条思路失败不会重新触发已经运行的风机思路。

### 7.4 用不同场景观察结果

每次更改启动表单中的 `scenario` 并新建一次流程：

| `scenario`  | 预设状态               | 并行流程的预期结果                           |
| ----------- | ---------------------- | -------------------------------------------- |
| `fan`       | 风机转速异常           | 滤网思路失败；重启风机后解决，生成降温图     |
| `filter`    | 滤网堵塞               | 风机思路失败；清理后解决，生成降温图         |
| `healthy`   | 初始温度正常           | 前置排查走“否”，不执行清理或重启             |
| `unknown`   | 超温但风量和转速都正常 | 两条思路均无匹配出口，整体排查失败           |
| `fan_stuck` | 风机卡死               | 重启方法抛出原始异常；任务失败，不到问题解决 |

`unknown` 是排查逻辑没有找到原因，`fan_stuck` 是业务方法执行报错。后者可在失败详情中查看 `simulator.py` 的原始 Python 堆栈。

每个场景只预设一种可恢复故障，避免把“解决一个原因”误当作“同时解决多个故障”。实际工程有多种故障并存时，需要另外设计联合验证和恢复策略。

选择 `scenario=fan` 时，先尝试滤网，判断不成立后继续风机，最后成功。选择 `scenario=filter` 时，第一条思路成功后默认暂停风机思路：选 **结束排查**，就不运行风机节点；选 **继续排查其余思路**，才开始风机检查，且不会重复清理滤网。

## 8. 在示例基础上设计更多排查思路

### 8.1 节点内容与连接

每个诊断节点都有名称和详细内容。新节点没有默认名称；填写详细内容后会按节点尺寸生成名称摘要。手动名称会保留，缩放节点时自动摘要随可用空间调整。**常规 → 节点类型**只供查看，不能编辑。结论只填名称时会复制为结论内容；只填内容时会生成名称摘要。

排查还需填写查看数据、获取方法、判断方法和参考文件；排查动作、处置措施应在详细内容中写清操作，结论应写清判断结论。没有完成的流程可先导出保存为草稿，但不一定能导出为可执行流程。

画图时遵循这些主要关系：开始先连接排查；排查动作后接排查；排查得出结论后，由结论进入处置措施；处置完成后可到问题解决。排查不能直接连接处置措施或问题解决，处置措施不能直接回连排查。跳转表示交接，具体交接目标仍需业务接入实现，不会仅凭节点文字自动运行另一张图。

排查用菱形，排查动作用正梯形，结论用矩形，处置措施用倒梯形，跳转用椭圆，问题解决用三角形，上升用五角星；深度诊断沿用原样式。可通过节点边框调整尺寸。界面校验会提示不符合规则的连接和缺失内容。

### 8.2 是／否分组与依赖

一个排查节点可以有“是”和“否”两组出口，每组可以连接多个不同节点，也可以只配置其中一组。修改画布上的连线名称为“是”“否”“yes”“no”即可修改分组，英文忽略大小写；其他名称不接受。

没有依赖关系的两种手段，可以并列连接到同一前置排查的同一组出口。必须先完成 A 才能执行 B 时，则将 B 接在 A 之后。并列连线的绘制先后不表示并行模式的优先级。

判断结果没有匹配出口时，记录当前思路失败；这与 Python 抛出异常不同：前者是正常的排查路径结果，后者是任务执行错误。

### 8.3 并行与串行

选中流程，在流程属性中选择排查模式：

| 发生的情况           | 并行排查                                   | 串行排查                                 |
| -------------------- | ------------------------------------------ | ---------------------------------------- |
| 同组有多个后续思路   | 同时启动，互不设优先级                     | 按顺序逐条尝试                           |
| 一条思路没有匹配出口 | 结束并记录该思路失败，其他已启动思路继续   | 继续下一条待排查思路                     |
| 到达问题解决         | 记录该路径成功，其他已启动路径按原流程继续 | 有剩余思路时默认暂停，用户选择结束或继续 |
| 所有思路都失败       | 整次排查失败                               | 整次排查失败                             |

串行模式下，选中连线，在 **执行顺序** 中填写数字，数字越小越先执行；未填写或数字相同时，保留连线在流程定义中的顺序。并行模式不使用这个顺序。多个处置措施连接到同一个问题解决节点是允许的；每条路径到达后继续处理，不要求额外增加等待所有路径的汇合网关。循环必须保留可达的退出路径。

同一对象上的方法可能被并行节点同时调用。是否允许并发、如何保护设备访问和共享状态，由业务工程自身处理。

## 9. 处理人工等待、回退和运行中断

### 9.1 主动要求人工判断

在排查节点打开 **人工判断／确认**：接口留空时直接等待人工；配置接口时先执行接口，再等待人工复核。这个开关只用于需要判断和分支的排查节点。

运行到该节点后，在 **Flowable 执行** 中刷新，查看依据和判断方法，选择“是”或“否”并继续。到达上升节点也会等待人工复核；串行排查成功后有剩余队列时，则会提供 **结束排查** 和 **继续排查其余思路**。

### 9.2 判断代码尚未实现时转人工

工程师可以使用平台提供的判断组件，明确请求人工接手。例如：

```python
from diagnostic_components import decision

@decision(instructions='确认电压曲线是否低于额定值')
def inspect_voltage(data):
    raise NotImplementedError('待接入自动判断')
```

通过组件产生的人工请求会交给界面处理，无需额外开启人工开关。也可继承 `DecisionComponent` 实现 `decide`，或直接返回 `HumanDecisionRequest`；返回请求对象本身即可。

只有组件未实现，或通过组件明确抛出 `NotImplementedError`，才会按此方式转人工。普通函数直接抛出该异常仍是任务失败；`pass` 或返回 `None` 也不等于未实现。同步与异步均支持。类方法更适合使用组件基类；装饰器取普通函数的第一个参数或名为 `data` 的参数作为判断依据。

worker 已提供 `diagnostic_components` 的导入路径；独立运行业务工程时需自行加入本仓库 `backend`。人工请求的可选选项应为“是／否”两组，或与该节点全部后继连线 ID 一致。该协议只用于排查节点。

### 9.3 回退重查

在排查或上升的人工等待中，可以选择**此前实际执行过的节点**，填写原因和可选的复查输入变量，再点击 **回退重查**。系统保留原有历史、旧结果和回退原因，清除需要重算的结果，然后从选中节点重新运行。

回退不会撤销已完成的设备动作，也不会把 Python 对象恢复到过去的状态；它是在当前实例上重跑，动作可能再次发生。当前节点、未执行节点和已结束实例不能作为任意回退入口，运行中的自动节点也不提供这一人工介入操作。串行成功暂停时使用继续／结束，不使用回退。

### 9.4 停止、重启和更新

Flowable 会保存流程进度和展示结果，但不会保存 Python 的全部内存。worker 或业务子进程重启后，旧流程无法自动恢复设备实例，会明确报会话丢失；不能从 `repr` 或历史结果还原原对象。

更新业务代码前，应先安排好正在运行的排查。修改代码后重新读取接口，并为新流程启动新版 worker；重启会丢失其当前会话。更改绑定、连线、分组或顺序后，还需重新导出执行包；旧实例继续使用对应的旧版 worker。worker 发现流程结束后会释放其业务会话；未结束的失败流程仍保留会话供后续处理。

## 10. 保存流程和参考文件

### 10.1 根据用途选择保存方式

| 需要保留什么                           | 选择哪个入口                   | 得到什么                              |
| -------------------------------------- | ------------------------------ | ------------------------------------- |
| 诊断逻辑与资源，便于移动和恢复         | **导出诊断项目**               | ZIP 中的 `workflow.json` 与 `assets/` |
| 布局、尺寸、颜色、字体等完整编辑状态   | **导出完整 BPMN**              | 完整 BPMN 编辑快照                    |
| 部署到 Flowable 执行                   | **Flowable 执行 → 导出执行包** | 第 6 节的三个执行文件                 |
| 生成离线 Python 工程，供工程师继续实现 | **导出 Python 骨架**           | 第 11 节说明的代码和资源              |

通用诊断项目的主定义是版本 4 的 `workflow.json`。它保留节点内容、接口绑定、连接、是／否分组、串行顺序和排查模式，不包含布局、尺寸、颜色、字体。资源独立放在目录中，JSON 只记录相对路径，不内嵌文件内容，也不额外保存一份 BPMN。

移动时将整个目录一起移动。恢复时选择 **导入项目目录**，读取 JSON 和资源并自动排版。单独导入 `workflow.json` 也能恢复节点和连线，但资源文件不在 JSON 中；若提示资源缺失，应改为导入完整目录。旧版 JSON 也可导入，缺少明确是／否分组的旧连线需补充。

这些导出文件不会打包业务 Python 工程、解释器或本机登记信息。换电脑后，还需准备业务工程及依赖、重新登记工程，并启动所需服务。

### 10.2 添加和打开参考文件

在节点的 **参考文件**中选择文件。常见图片、PDF、文本、CSV、Markdown、JSON 和部分音视频可在界面预览，具体取决于浏览器支持。HTML、SVG、XML 等活动文档及其他类型通过 Windows 本机服务交给本机软件打开。

没有默认关联时会弹出系统软件选择器；脚本、可执行文件和快捷方式始终要求选择查看软件。外部软件打开的是临时副本，修改不会自动写回项目；需要更新时，保存修改后的文件并重新选择它。

单个参考文件最大 50 MiB。部署和启动请求的合计上限为 70 MiB，包含传输编码及 JSON 开销，因此多个大文件的总大小也会影响能否部署。保存通用项目时仍按相对路径输出到资源目录。

需要让业务 Python 代码读取同一文件时，应在工程中按实际路径读取，并随工程部署该文件。给节点附上参考文件不会自动给函数增加文件参数，也不会自动修改 Python 代码中的路径。

## 11. 其他运行方式与高级设置

### 11.1 结构模拟

**开启结构模拟**只展示 BPMN 令牌流动。它允许未绑定 Python 的节点参与动画，不验证函数、参数、真实判断结果或诊断的串行暂停规则。检查业务执行请使用 **Flowable 执行**。

### 11.2 导出离线 Python 骨架

没有现成工程、希望工程师从流程内容开始实现时，可以选择 **导出 Python 骨架**。它保留同一份 `workflow.json` 和资源，另外生成运行器与业务文件；它不会自动执行图上已保存的外部模块绑定。

解压到新目录，使用 Python 3.10+ 运行：

```powershell
python runner.py
python runner.py --data inputs.json --no-images
```

先打开生成的 `IMPLEMENTATION.md`，按节点 ID 找到对应业务函数。每个函数开头都标明节点内容、输入输出、调用关系和后继。文件分工如下：

| 文件                      | 需要实现的工作                     |
| ------------------------- | ---------------------------------- |
| `acquisition.py`          | 原始采集                           |
| `parsing.py`              | 解析、校验、单位转换，默认原样返回 |
| `display.py`              | 图表与参考文件展示                 |
| `diagnosis.py`            | 自动判断                           |
| `actions.py`              | 业务动作                           |
| `routing.py`、`runner.py` | 已生成的流程调度，通常无需修改     |

采集、判断和动作的明确 `NotImplementedError` 占位会转为命令行人工兜底；其他异常仍停止执行，解析或展示错误不会被当作成功。默认动作需要人工完成后输入 `yes` 确认。

把 `inputs.example.json` 复制为 `inputs.json`，按节点 ID 填入已知采集数据，可跳过对应采集并继续解析和判断。命令行采集也可输入文本、JSON 或 `@JSON文件路径`。`--no-images`关闭自动打开参考文件，默认最大执行 1000 步，可用 `--max-steps` 调整；业务函数超时由工程自行管理。

离线调用链为 `runner → acquisition → parsing → display → diagnosis → routing → 后继`；动作由 `runner → actions` 调用。工程师可在这些函数中导入已有业务包。`Context.ask/show` 可替换界面，`context.data[节点ID]` 保存 `raw/parsed/result`。程序接入可使用 `run(supplied={节点ID: 原始数据})`；串行暂停后，用返回的 `state` 传入 `run(..., resume=state, success_action='continue'|'finish')` 恢复。

离线骨架还支持普通嵌套子流程和排他选择，条件文本仅展示、不执行表达式。跳转表示交接，不会自动运行目标链路。不要据此推断同一张图也能部署到当前 Flowable 编译器。

重新生成时使用新目录，按稳定的节点 ID 迁移已有实现，避免覆盖业务代码；`node_N` 的编号会随导出顺序变化。

### 11.3 worker 和服务的其他配置

| 情况                              | 做法                                                                                                    |
| --------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 登记信息不在默认位置              | worker 增加 `--registry D:/config/projects.json`                                                        |
| 未登记的旧模块仍需运行            | worker 用可重复的 `--project D:/equipment/diagnostics` 提供根目录；未匹配登记时使用 worker 自己的解释器 |
| 同名模块登记在多个目录            | 用 `--project`指定当前工程目录，避免来源不唯一                                                          |
| 业务调用需要更长时间              | worker 增加 `--timeout 600`；调试超时则调整后端的 `--timeout`                                           |
| 无完整 Maven 缓存但已有可执行 JAR | 可用 `scripts/rebuild-flowable-local.py` 从现有依赖离线重编；正常构建仍用 Maven                         |

`--project` 和 `--registry` 的完整命令及环境配置见 [Flowable 技术说明](../backend/FLOWABLE.zh-CN.md)。桌面绘图库若要求主线程或交互桌面，应由业务入口自行启动适合的桌面进程；业务接口在工作线程中调用。

当前 Flowable 编译支持一个顶层流程、一个普通开始事件和本项目的诊断节点。不接受子流程、复杂事件、普通并行网关、手写条件表达式或默认分支。需要并行时使用诊断连线和排查模式，需要判断时使用排查的是／否结果。

旧的显式参数映射继续支持 `$节点ID.字段`、`$变量名`、`$`（全部变量）、数组／字典路径和 `$$`（转义美元符）；新接入通常不需要使用。

## 12. 遇到问题时从哪一步检查

| 现象                   | 先检查什么                                   | 下一步                                                   |
| ---------------------- | -------------------------------------------- | -------------------------------------------------------- |
| Python 项目无法连接    | 本机后端是否运行，页面来源和代理端口是否匹配 | 按第 2 节重新确认启动地址                                |
| 接入时导入失败         | 工程目录、模块名、解释器和依赖是否正确       | 在该解释器中确认模块可导入；模块填可导入名称而非文件路径 |
| 列表没有所需接口       | 是否公开、是否重导出、工厂是否有返回类注解   | 调整导出或注解后重新读取接口                             |
| 参数缺失或来源不唯一   | 参数名、节点标识、启动输入和已执行结果       | 按第 5 节确定唯一数据来源，不能仅凭签名推断实际值        |
| 动画能走但实际没有结果 | 是否只运行了结构模拟，worker 是否启动        | 使用正确执行包启动 worker，再查看真实流程                |
| 自动任务一直等待       | Java 服务是否运行，worker 是否监听当前执行包 | 检查终端中的 `Subscribed:` 及所用 `bindings.json`        |
| worker 提示已存在      | 同一执行包是否重复启动                       | 使用已启动的协调器；一次可运行多个流程                   |
| 没有进入预期分支       | 排查返回值是否明确、对应出口是否存在         | 区分正常的“思路失败”和 Python 任务报错                   |
| Python 任务失败        | 失败详情中的原始异常堆栈                     | 根据业务文件和调用位置处理；动作重跑可能再次作用于设备   |
| 报会话丢失             | worker 或业务子进程是否重启                  | 根据实际设备状态处理后新建排查；历史不能恢复内存对象     |
| 资源丢失或无法打开     | 是否只导入了 JSON、本机是否有对应软件        | 导入完整目录，或选择支持该文件的软件                     |
| 回退后设备状态未还原   | 是否把回退理解成撤销                         | 回退是重新执行，设备动作和对象状态不会自动倒退           |

更底层的接口与运行说明见 [Python 接入说明](../backend/README.md) 和 [Flowable 技术说明](../backend/FLOWABLE.zh-CN.md)。
