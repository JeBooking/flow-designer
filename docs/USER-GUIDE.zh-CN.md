# 诊断流程用户手册

[English](USER-GUIDE.md) | [中文](USER-GUIDE.zh-CN.md)

本手册从你自己的 Python 业务工程开始。下列路径、模块、类和方法均为占位示意，请替换为工程中真实可用的值；平台不会创建业务实现或安装业务依赖。

## 1. 各部分负责什么

画布定义依赖和诊断路径；Python 接口负责采集、计算、设备访问和处置；Flowable 负责真实调度、人工等待与历史。**Python 项目**用于登记和调试，**诊断执行**用于运行当前画布。结构模拟仅播放令牌，不会执行 Python。

## 2. 首次准备与每次启动

首次需要 Java 21、Maven 3.9、Python 3.9+、Node 和 pnpm。在仓库根目录准备：

```powershell
pnpm install
python -m venv backend/.local/venv
backend/.local/venv/Scripts/python.exe -m pip install -r backend/requirements-flowable.txt
cd flowable-runtime
mvn package
cd ..
```

这一步构建 `flowable-runtime/target/diagnostic-flowable-1.0.0.jar` 并安装官方 `flowable.external-worker-client==1.0.2`。非 Windows 环境使用 `backend/.local/venv/bin/python`。已有环境可复用。业务依赖应单独装在业务项目解释器中，启动器不会安装依赖、下载 Java 或 Python。

每次运行只需：

```powershell
pnpm dev
```

打开 `http://127.0.0.1:5173/vue-bpmn-designer/`。启动器统一管理前端、本机后端（8765）和本地 Flowable（8080），仅复用通过身份、认证与配置一致性检查的服务；启动失败查看 `backend/.local/logs/`。`JAVA_HOME` 可指定 Java，`PYTHON` 可指定平台解释器，否则优先本地 venv，再检查 PATH。

默认 Flowable 地址为 `http://127.0.0.1:8080`，账号 `diagnostic`、密码 `local-demo`。可设置 `FLOWABLE_USER`、`FLOWABLE_PASSWORD`。明确设置 `FLOWABLE_URL` 时只连接该外部引擎，不会另起本地替代；复用后端必须使用相同引擎地址。

已有 `dist/index.html` 时运行 `pnpm start`，打开 `http://127.0.0.1:8765/vue-bpmn-designer/`。构建使用 `pnpm build`。`pnpm dev:frontend` 只启动前端，供开发使用。

## 3. 登记自己的 Python 工程

在顶部 **Python 项目** 填写：

| 字段 | 占位示意 | 含义 |
| --- | --- | --- |
| 项目目录 | `D:/your-project` | 已有业务工程根目录 |
| 入口模块 | `your_package.api` | 可导入模块名，不是文件名 |
| 解释器 | `D:/your-project/.venv/Scripts/python.exe` | 已安装业务依赖的 Python |
| 类或工厂（可选） | `YourDevice` | 真实类名或工厂函数名；留空使用模块函数 |
| 名称（可选） | 你的设备诊断 | 便于辨认 |

工程不会被复制，登记不会安装依赖。相对路径以仓库根目录为起点；导入路径包含业务工程的 `src/`、根目录和父目录，工作目录为工程根目录。模块函数按 `__all__` 导出，未定义时发现入口模块自身的公开函数。

类登记只检查签名，不创建实例；构造参数在运行时按同名启动变量或默认值提供。有返回类注解的工厂也可免调用发现；无注解工厂会用默认值临时创建对象，若有必填参数应补充返回类注解。

## 4. 调试接口并绑定自己的画布

先按签名填写调试输入，调用工程实际接口，确认解释器、依赖和设备连接正常。连续调试共享会话，**重置会话**会丢弃对象和结果。调试会调用真实业务代码，设备动作按现场规程处理；调试会话与流程运行会话独立。

新建自己的图，或导入自己保存的 BPMN、`workflow.json` 或项目目录。导入前保存当前画布。按第 8 节配置诊断内容、参考文件与是／否连接，再在节点的 **Python 工程** 和 **调用接口** 选择已登记工程和方法。入口模块和类来自项目登记，不需要逐节点重复填写。

排查应返回明确的 `True`/`False`、`yes`/`no` 或含 `next` 的字典。结论可以只记录文本；动作允许无输入及返回 `None`。最终节点不绑定业务逻辑。

## 5. 参数与原生对象

自动匹配依次使用兼容的旧映射、同名启动变量、与参数同名的节点 ID 所保存的完整结果、上游字典中唯一的同名字段及函数默认值。缺失或歧义会显示具体参数，不会凭接口签名猜测数据。

例如工程中实际存在 `collect()` 和 `assess(reading)` 时，可将采集节点标识设为 `reading`，让后续参数取得完整采集对象。这里的方法名仅作说明，不是平台提供的接口。位置专用参数、异步接口、无参数函数均可使用。

同一流程的同一工程共享常驻隔离 Python 进程和类实例，普通模块函数也保留全局状态。不同流程互相隔离，不同工程不能直接共享原生对象引用；并行调用的线程安全由业务工程负责。原始对象留在 Python，界面只展示 JSON 投影、类型和文字表示，`repr` 不会作为原对象传给下一节点。

## 6. 开始执行当前流程

1. 打开 **诊断执行**，确认当前画布的节点、连接和绑定。
2. 按已登记类／工厂签名填写启动输入，留空保留默认值；额外数据可添加名称／值行。必要时展开高级初始变量 JSON，并启用 **使用 JSON 代替表单**；此时只用 JSON，不合并表单。
3. 点击 **开始执行**。后端校验当前定义，自动准备匹配的 worker 并部署启动流程。正常运行不需要下载执行包或手工启动 worker。
4. 观察自动更新的画布节点状态、执行路径与结果卡片。人工等待时按提示确认、选择分支或回退。不要把结构模拟的动画当成真实执行结果。

每次开始使用当前画布配置创建新实例，不复用之前的调试对象；更改画布不会改变已运行实例。状态来自实际 Flowable 运行，正在执行、等待人工、任务报错和已结束应分别处理。

## 7. 查看结果和定位错误

结果卡片显示业务接口返回值；只有结果字典包含 `chartSvg` 字符串时才展示相应图表。返回文件路径不会自动显示图像，平台不会生成示意业务曲线冒充运行结果。

原始活动历史、变量和异常信息放在默认折叠的 **原始执行详情** 中。Python 失败时展开错误详情查看 traceback，按业务文件和调用位置排查；`backend/.local/logs/` 记录服务日志，worker 日志路径为 `backend/.local/executions/<内容哈希>/<启动UUID>.log`。目录按执行定义的内容哈希区分，每次 worker 启动使用独立的 UUID 日志。思路无匹配分支属于诊断失败，不等同于 Python 异常。

## 8. 设计诊断节点与排查思路

### 8.1 节点内容与连接

每个诊断节点都有名称和详细内容。新节点没有默认名称；填写详细内容后会按节点尺寸生成名称摘要。手动名称会保留，缩放节点时自动摘要随可用空间调整。**常规 → 节点类型**只供查看，不能编辑。结论只填名称时会复制为结论内容；只填内容时会生成名称摘要。

排查还需填写查看数据、获取方法、判断方法和参考文件；排查动作、处置措施应在详细内容中写清操作，结论应写清判断结论。没有完成的流程可先导出保存为草稿，但不一定能开始执行。

画图时遵循这些主要关系：开始先连接排查；排查动作后接排查；排查得出结论后，由结论进入处置措施；处置完成后可到问题解决。排查不能直接连接处置措施或问题解决，处置措施不能直接回连排查。跳转表示交接，具体交接目标仍需业务接入实现，不会仅凭节点文字自动运行另一张图。

排查用菱形，排查动作用正梯形，结论用矩形，处置措施用倒梯形，跳转用椭圆，问题解决用三角形，上升用五角星；深度诊断沿用原样式。可通过节点边框调整尺寸。界面校验会提示不符合规则的连接和缺失内容。

### 8.2 是／否分组与依赖

一个排查节点可以有“是”和“否”两组出口，每组可以连接多个不同节点，也可以只配置其中一组。修改画布上的连线名称为“是”“否”“yes”“no”即可修改分组，英文忽略大小写；其他名称不接受。

没有依赖关系的两种手段，可以并列连接到同一前置排查的同一组出口。必须先完成 A 才能执行 B 时，则将 B 接在 A 之后。并列连线的绘制先后不表示并行模式的优先级。

判断结果没有匹配出口时，记录当前思路失败；这与 Python 抛出异常不同：前者是正常的排查路径结果，后者是任务执行错误。

### 8.3 并行与串行

选中流程，在流程属性中选择排查模式：

| 发生的情况           | 并行排查                                   | 串行排查                                 |
| -------------------- | ------------------------------------------ | ---------------------------------------- |
| 同组有多个后续思路   | 同时启动，互不设优先级                     | 按顺序逐条尝试                           |
| 一条思路没有匹配出口 | 结束并记录该思路失败，其他已启动思路继续   | 继续下一条待排查思路                     |
| 到达问题解决         | 记录该路径成功，其他已启动路径按原流程继续 | 有剩余思路时默认暂停，用户选择结束或继续 |
| 所有思路都失败       | 整次排查失败                               | 整次排查失败                             |

串行模式下，选中连线，在 **执行顺序** 中填写数字，数字越小越先执行；未填写或数字相同时，保留连线在流程定义中的顺序。并行模式不使用这个顺序。多个处置措施连接到同一个问题解决节点是允许的；每条路径到达后继续处理，不要求额外增加等待所有路径的汇合网关。循环必须保留可达的退出路径。

同一对象上的方法可能被并行节点同时调用。是否允许并发、如何保护设备访问和共享状态，由业务工程自身处理。

## 9. 处理人工等待、回退和运行中断

八张流程图的工程登记、导入步骤、触发条件和复核操作，见本手册[第 13 节：自动判断与人工接管示例](#13-示例自动判断与人工接管)。

### 9.1 主动要求人工判断

在排查节点打开 **人工判断／确认**：接口留空时直接等待人工；配置接口时先执行接口，再等待人工复核。这个开关只用于需要判断和分支的排查节点。

运行到该节点后，在 **诊断执行** 的自动更新状态中，查看依据和判断方法，选择“是”或“否”并继续。到达上升节点也会等待人工复核；串行排查成功后有剩余队列时，则会提供 **结束排查** 和 **继续排查其余思路**。

### 9.2 判断代码尚未实现时转人工

工程师可以使用平台提供的判断组件，明确请求人工接手。例如：

```python
from diagnostic_components import decision

@decision(instructions='确认电压曲线是否低于额定值')
def inspect_voltage(data):
    raise NotImplementedError('待接入自动判断')
```

通过组件产生的人工请求会交给界面处理，无需额外开启人工开关。也可继承 `DecisionComponent` 实现 `decide`，或直接返回 `HumanDecisionRequest`；返回请求对象本身即可。

只有组件未实现，或通过组件明确抛出 `NotImplementedError`，才会按此方式转人工。普通函数直接抛出该异常仍是任务失败；`pass` 或返回 `None` 也不等于未实现。同步与异步均支持。类方法更适合使用组件基类；装饰器取普通函数的第一个参数或名为 `data` 的参数作为判断依据。

worker 已提供 `diagnostic_components` 的导入路径；独立运行业务工程时需自行加入本仓库 `backend`。人工请求的可选选项应为“是／否”两组，或与该节点全部后继连线 ID 一致。该协议只用于排查节点。

### 9.3 回退重查

在排查或上升的人工等待中，可以选择**此前实际执行过的节点**，填写原因和可选的复查输入变量，再点击 **回退重查**。系统保留原有历史、旧结果和回退原因，清除需要重算的结果，然后从选中节点重新运行。

回退不会撤销已完成的设备动作，也不会把 Python 对象恢复到过去的状态；它是在当前实例上重跑，动作可能再次发生。当前节点、未执行节点和已结束实例不能作为任意回退入口，运行中的自动节点也不提供这一人工介入操作。串行成功暂停时使用继续／结束，不使用回退。

### 9.4 停止、重启和更新

关闭执行抽屉仅暂停轮询，后台流程继续；在同一面板重新打开抽屉会恢复监控。刷新页面或重建 modeler 不会恢复对旧实例的监控。按 Ctrl+C 退出应用启动器会停止它自己启动的服务与自有 worker，复用的外部服务不会被关闭。结束应用或回退均不能撤销已发出的设备动作，应按业务规程安排运行中的设备与排查。

任务进入死信后，可点击 **重新执行当前流程**，确认后按当前图新建实例。这不会取消旧实例，也不会撤销已完成的设备动作，同一动作可能再次执行。旧实例 ID 会保留在当前面板中，刷新页面或重建 modeler 前应自行记录。

Flowable 会保存流程进度和展示结果，但不会保存 Python 的全部内存。worker 或业务子进程重启后，旧流程无法自动恢复设备实例，会明确报会话丢失；不能从 `repr` 或历史结果还原原对象。

更新业务代码前，应先安排好正在运行的排查。修改代码后重新读取接口；新流程点击“开始执行”时自动准备匹配的 worker。更改绑定、连线、分组或顺序后，新启动使用当前定义，旧实例保持原定义；不要为更新新图而终止旧实例的 worker。重启服务会丢失当前会话。worker 发现流程结束后会释放其业务会话；未结束的失败流程仍保留会话供后续处理。

## 10. 保存流程和参考文件

### 10.1 根据用途选择保存方式

| 需要保留什么                           | 选择哪个入口                   | 得到什么                              |
| -------------------------------------- | ------------------------------ | ------------------------------------- |
| 诊断逻辑与资源，便于移动和恢复         | **导出诊断项目**               | ZIP 中的 `workflow.json` 与 `assets/` |
| 布局、尺寸、颜色、字体等完整编辑状态   | **导出完整 BPMN**              | 完整 BPMN 编辑快照                    |
| 在 Flowable 执行当前图                 | **诊断执行 → 开始执行**       | 实际流程实例与在线执行结果            |
| 生成离线 Python 工程，供工程师继续实现 | **导出 Python 骨架**           | 第 11 节说明的代码和资源              |

通用诊断项目的主定义是版本 4 的 `workflow.json`。它保留节点内容、接口绑定、连接、是／否分组、串行顺序和排查模式，不包含布局、尺寸、颜色、字体。资源独立放在目录中，JSON 只记录相对路径，不内嵌文件内容，也不额外保存一份 BPMN。

移动时将整个目录一起移动。恢复时选择 **导入项目目录**，读取 JSON 和资源并自动排版。单独导入 `workflow.json` 也能恢复节点和连线，但资源文件不在 JSON 中；若提示资源缺失，应改为导入完整目录。旧版 JSON 也可导入，缺少明确是／否分组的旧连线需补充。

这些导出文件不会打包业务 Python 工程、解释器或本机登记信息。换电脑后，还需准备业务工程及依赖、重新登记工程，并启动所需服务。

### 10.2 添加和打开参考文件

在节点的 **参考文件**中选择文件。常见图片、PDF、文本、CSV、Markdown、JSON 和部分音视频可在界面预览，具体取决于浏览器支持。HTML、SVG、XML 等活动文档及其他类型通过 Windows 本机服务交给本机软件打开。

没有默认关联时会弹出系统软件选择器；脚本、可执行文件和快捷方式始终要求选择查看软件。外部软件打开的是临时副本，修改不会自动写回项目；需要更新时，保存修改后的文件并重新选择它。

单个参考文件最大 50 MiB。部署和启动请求的合计上限为 70 MiB，包含传输编码及 JSON 开销，因此多个大文件的总大小也会影响能否部署。保存通用项目时仍按相对路径输出到资源目录。

需要让业务 Python 代码读取同一文件时，应在工程中按实际路径读取，并随工程部署该文件。给节点附上参考文件不会自动给函数增加文件参数，也不会自动修改 Python 代码中的路径。

## 11. 其他运行方式与高级设置

### 11.1 结构模拟

**开启结构模拟**只展示 BPMN 令牌流动。它允许未绑定 Python 的节点参与动画，不验证函数、参数、真实判断结果或诊断的串行暂停规则。检查业务执行请使用 **诊断执行**。

### 11.2 导出离线 Python 骨架

没有现成工程、希望工程师从流程内容开始实现时，可以选择 **导出 Python 骨架**。它保留同一份 `workflow.json` 和资源，另外生成运行器与业务文件；它不会自动执行图上已保存的外部模块绑定。

解压到新目录，使用 Python 3.10+ 运行：

```powershell
python runner.py
python runner.py --data inputs.json --no-images
```

先打开生成的 `IMPLEMENTATION.md`，按节点 ID 找到对应业务函数。每个函数开头都标明节点内容、输入输出、调用关系和后继。文件分工如下：

| 文件                      | 需要实现的工作                     |
| ------------------------- | ---------------------------------- |
| `acquisition.py`          | 原始采集                           |
| `parsing.py`              | 解析、校验、单位转换，默认原样返回 |
| `display.py`              | 图表与参考文件展示                 |
| `diagnosis.py`            | 自动判断                           |
| `actions.py`              | 业务动作                           |
| `routing.py`、`runner.py` | 已生成的流程调度，通常无需修改     |

采集、判断和动作的明确 `NotImplementedError` 占位会转为命令行人工兜底；其他异常仍停止执行，解析或展示错误不会被当作成功。默认动作需要人工完成后输入 `yes` 确认。

把 `inputs.example.json` 复制为 `inputs.json`，按节点 ID 填入已知采集数据，可跳过对应采集并继续解析和判断。命令行采集也可输入文本、JSON 或 `@JSON文件路径`。`--no-images`关闭自动打开参考文件，默认最大执行 1000 步，可用 `--max-steps` 调整；业务函数超时由工程自行管理。

离线调用链为 `runner → acquisition → parsing → display → diagnosis → routing → 后继`；动作由 `runner → actions` 调用。工程师可在这些函数中导入已有业务包。`Context.ask/show` 可替换界面，`context.data[节点ID]` 保存 `raw/parsed/result`。程序接入可使用 `run(supplied={节点ID: 原始数据})`；串行暂停后，用返回的 `state` 传入 `run(..., resume=state, success_action='continue'|'finish')` 恢复。

离线骨架还支持普通嵌套子流程和排他选择，条件文本仅展示、不执行表达式。跳转表示交接，不会自动运行目标链路。不要据此推断同一张图也能部署到当前 Flowable 编译器。

重新生成时使用新目录，按稳定的节点 ID 迁移已有实现，避免覆盖业务代码；`node_N` 的编号会随导出顺序变化。

### 11.3 可选运维配置（不属于普通运行步骤）

| 情况                              | 做法                                                                                                    |
| --------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 登记信息不在默认位置              | worker 增加 `--registry D:/config/projects.json`                                                        |
| 未登记的旧模块仍需运行            | worker 用可重复的 `--project D:/equipment/diagnostics` 提供根目录；未匹配登记时使用 worker 自己的解释器 |
| 同名模块登记在多个目录            | 用 `--project`指定当前工程目录，避免来源不唯一                                                          |
| 业务调用需要更长时间              | worker 增加 `--timeout 600`；调试超时则调整后端的 `--timeout`                                           |
| 无完整 Maven 缓存但已有可执行 JAR | 可用 `scripts/rebuild-flowable-local.py` 从现有依赖离线重编；正常构建仍用 Maven                         |

`--project` 和 `--registry` 的完整命令及环境配置见 [Flowable 技术说明](../backend/FLOWABLE.zh-CN.md)。桌面绘图库若要求主线程或交互桌面，应由业务入口自行启动适合的桌面进程；业务接口在工作线程中调用。

当前 Flowable 编译支持一个顶层流程、一个普通开始事件和本项目的诊断节点。不接受子流程、复杂事件、普通并行网关、手写条件表达式或默认分支。需要并行时使用诊断连线和排查模式，需要判断时使用排查的是／否结果。

旧的显式参数映射继续支持 `$节点ID.字段`、`$变量名`、`$`（全部变量）、数组／字典路径和 `$$`（转义美元符）；新接入通常不需要使用。

## 12. 遇到问题时从哪一步检查

| 现象                   | 先检查什么                                   | 下一步                                                   |
| ---------------------- | -------------------------------------------- | -------------------------------------------------------- |
| Python 项目无法连接    | 本机后端是否运行，页面来源和代理端口是否匹配 | 按第 2 节重新确认启动地址                                |
| 接入时导入失败         | 工程目录、模块名、解释器和依赖是否正确       | 在该解释器中确认模块可导入；模块填可导入名称而非文件路径 |
| 列表没有所需接口       | 是否公开、是否重导出、工厂是否有返回类注解   | 调整导出或注解后重新读取接口                             |
| 参数缺失或来源不唯一   | 参数名、节点标识、启动输入和已执行结果       | 按第 5 节确定唯一数据来源，不能仅凭签名推断实际值        |
| 动画能走但实际没有结果 | 是否只运行了结构模拟，worker 是否启动        | 运行 pnpm dev，并在诊断执行点击开始执行                |
| 自动任务一直等待       | Java 服务状态、启动错误及 worker 日志 | 查看 `backend/.local/logs/` 与 `backend/.local/executions/<内容哈希>/<启动UUID>.log`        |
| worker 提示已存在      | 是否与其他后端或手工 worker 冲突                       | 保留一个应用后端管理器，清理明确自有的冲突服务                   |
| 没有进入预期分支       | 排查返回值是否明确、对应出口是否存在         | 区分正常的“思路失败”和 Python 任务报错                   |
| Python 任务失败        | 失败详情中的原始异常堆栈                     | 根据业务文件和调用位置处理；动作重跑可能再次作用于设备   |
| 报会话丢失             | worker 或业务子进程是否重启                  | 根据实际设备状态处理后新建排查；历史不能恢复内存对象     |
| 资源丢失或无法打开     | 是否只导入了 JSON、本机是否有对应软件        | 导入完整目录，或选择支持该文件的软件                     |
| 回退后设备状态未还原   | 是否把回退理解成撤销                         | 回退是重新执行，设备动作和对象状态不会自动倒退           |

更底层的接口与运行说明见 [Python 接入说明](../backend/README.md) 和 [Flowable 技术说明](../backend/FLOWABLE.zh-CN.md)。

## 13. 示例：自动判断与人工接管

这个独立 Python 工程演示自动分支、人工复核、判断组件兜底和预期的 Python 失败。工程没有工厂入口，
业务代码不需要第三方依赖，只使用传入的电压数据，不采集或操作设备。

### 13.1 准备与工程登记

先完成[用户指南中的平台准备](#2-首次准备与每次启动)，
再在仓库根目录执行 `pnpm dev`，由启动器统一管理所需服务和 worker。

打开 **Python 项目**，登记以下信息：

| 字段 | 内容 |
| --- | --- |
| 项目目录 | `backend/examples/manual_handling_project`（相对仓库根目录） |
| 入口模块 | `manual_handling` |
| 解释器 | 本机 Python 3.9+ 解释器的可执行文件路径 |
| 类或工厂 | 留空，使用模块函数 |
| 名称 | 便于识别即可，例如 `人工接管示例` |

纯人工图也需要登记这个模块，因为后续的记录动作会调用 `record_result()`。业务解释器无需安装
Flowable SDK；平台 worker 会提供 `diagnostic_components` 的导入路径，不要把它当作第三方依赖安装。

### 13.2 导入与启动

建议先导入 **05-decorator-fallback.bpmn**：它能直接展示尚未实现的自动判断如何保留依据并转入人工复核。

1. 导入前先保存当前画布。
2. 在设计器主界面使用 **导入 BPMN 或 workflow.json**，选择本工程 [diagrams](../backend/examples/manual_handling_project/diagrams/) 目录中的一个
   独立 `.bpmn` 文件。这些文件不放进执行界面的示例菜单；启动应用也不会自动用示例替换画布。
3. 选中排查节点 Check，对照下表查看 **Python 项目**、**调用接口** 和 **人工判断／确认**。
   如果导入的绑定尚未关联本机登记项，选择刚登记的工程；记录节点 Record 也应选择同一工程和
   `record_result()`。纯人工图的 Check 故意不绑定 Python。
4. 打开 **诊断执行**，点击 **开始执行**。默认电压为 `21.2` V；要演示自动走“是”，在开始新实例前，
   添加名称为 `voltage`、数值为 `24` 的额外启动输入。不添加则使用默认值，自动图走“否”。

纯人工图使用节点说明中的静态示例 `21.2` V。它的 Check 不调用 Python，启动输入 `voltage`
不会改变这段说明或其中的示例依据。

每张图都是 Start → Check；“是”经过 Conclusion → Record → Problem Solved（问题解决），
“否”到 Escalation（上升）。`record_result()` 仅作为示例记录步骤，返回 `None`，不写文件、不操作设备。

### 13.4 在复核卡片中操作

人工处理位于右侧 **诊断执行** 抽屉内的 **诊断复核** 卡片，不会自动弹出独立窗口。
关闭抽屉后，需要自行重新打开，才能继续监控当前实例。

运行图 02–06 时，查看判断依据和参考／判断方法说明。Python 提供的默认依据为
`voltage: 21.2`、`threshold: 22`、`unit: V`；纯人工图通过节点说明提供背景。
在 **下一步** 中选择“是”或“否”，再点 **确认并继续**。判断问题是“电压是否大于或等于 22 V”，
所以默认依据对应“否”；也可以人工选择另一分支来观察流程行为。

- 选“是”：经过结论和记录动作，到问题解决。
- 选“否”：到上升后还会等待一次，需要点击 **确认上升并结束**。图 01 默认自动走“否”时也会有这次等待。
- 图 07：应看到 Python 调用失败，展开错误详情中的 **原始 Python 异常堆栈**，定位故意抛出的异常。
  这不是成功的人工兜底，也不表示已经完成人工复核。
- 图 08：排查没有返回分支判断，应出现 `ValueError`；同样在错误详情中查看 traceback，不应出现人工复核。

### 13.5 能力边界

只有组件协议会把尚未实现的判断转成人工处理；普通 `pass` 或返回 `None` 不会主动请求人工复核，
图 08 专门演示这一边界。图 03 等待人工是因为开启了节点人工开关，不是因为返回依据就会自动兜底。

这些示例覆盖的是排查判断。执行界面目前没有用于手工填写采集结果、确认任意业务动作完成的统一表单，
不能把“是／否”复核当作这些能力。本说明描述预期行为，不代表已在你的机器上实机运行通过。

工程文件与独立说明见[示例工程 README](../backend/examples/manual_handling_project/README.zh-CN.md)。
