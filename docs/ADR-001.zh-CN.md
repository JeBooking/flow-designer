## 1. 背景

现架构为三层：Vue + bpmn-js 画布、Python 后端、Flowable（Java 引擎）。

已核实的现状事实：

- 串行模式下 `serial_workflow` 把诊断图压平：原图的 sequenceFlow、网关、事件被替换，
  统一连到一个 `diagnostic_dispatch` 独占网关，出边条件为 `${diagnosticNext == "nodeId"}`。
- 串行路由由 `DiagnosisScheduler` 维护的 `diagnosticQueue` / `diagnosticNext` 决定；
  并行路由仍由 Flowable 网关和独立 token 执行，两种模式都记录路径和最终状态。
- Flowable 实际承担：持久化等待、人工任务、执行历史、事务、并发、变量作用域。
- 连线规则已统一读取 `src/rules/diagnosis-connections.json`，前端与编译器共用。
- 模块接入方式为节点上填 `pythonModule / pythonFunction` 字符串，参数按签名运行时匹配；
  多个上游出现同名字段时抛 `Ambiguous`；判断返回值由 `decision_branch` 运行时猜 `yes/no`。
- topic 形如 `{process_id}.{version}.{pythonTopic|nodeId}`，自带流程版本，不是模块身份。
- 会话键为 `(process_instance_id, project_key)`，`callActivity` 子流程实例 ID 不同，会命中
  「Python 会话已丢失」分支。
- 编译白名单仅接受 `task` / `startEvent` / `sequenceFlow` / `documentation` / `extensionElements`，
  `subProcess` 与 `boundaryEvent` 均被拒绝。

用户已确认的硬需求：「保存现场」必须保留——流程停在节点等人工确认，等待期间不占进程，重启能续跑。

## 2. 决策

采用 **能力契约为主干、接缝为配套** 的组合，不整体更换执行内核。

三个层面分开决策，不混为一谈：

| 层面 | 决策 |
|---|---|
| 模块接入 | 改为能力契约（唯一直接兑现「子仓库接入」诉求） |
| 代码组织 | 收敛 4 个接缝，其中 2 项立即落地 |
| 执行内核 | 维持 Flowable，不替换；但保留替换出口 |

### 2.1 全局优先级规则

**declared overrides derived, derived fills gaps, conflict → 编译告警一次并采用 declared。**

适用于 `outputs`、`suspend`、`errors`、`idempotent` 等所有「既可声明又可推导」的字段。

没有这条规则，多条派生规则之间会互相打架：例如能力声明 `suspend: never`，而 opaque 规则又推导出
「该能力必须留驻等待」，两者会各自生成一个 userTask，且没有任何一处能发现冲突。

## 3. 模块契约规范

### 3.1 节点绑定

画布节点存 `capabilityRef: "<id>@<range>"`，不再存 `module / function` 字符串。
能力 ID 为稳定语义标识（如 `data.fetch.modbus`），与模块物理路径解耦。

### 3.2 manifest 与 fail-closed

- 磁盘上的 `diagnosis.module.json` 可选；**但本次部署必须产出一份 schema**。
- 缺失时由现有 `describe()` / `parameter_info` 从类型注解自动推导，不要求作者手写。
- **推导结果必须落盘进版本库**（`.diagnosis/manifest.json`）；否则修改函数签名等于静默修改契约，
  git 与 CI 都无法察觉。
- 推导产物标记 `origin: "derived"` 且 `open: true`。`open` 为真时禁用分支静态校验，
  但把「未声明出口的能力数」计入 CI 输出，避免用 `outputs: unknown` 绕过目的。
- 注册中心 schema 为空即编译失败，不降级为警告。

### 3.3 outputs 按能力类型声明

- `decision` → `next: enum[yes, no]`
- `action` → `{}`
- `display` → `chartSvg?: string`
- 数据类能力 → 显式字段清单

统一字段声明是错误的（返回值有四种形态），必须按能力类型分列。

### 3.4 原生对象

保留 `opaque<T>`：原生对象不出进程，跨节点只传引用 ID，投影沿用现有
`native / pythonType / representation`。

### 3.5 rules 层隔离

`rules/*.json` 中禁止出现 `module / factory / function` 字样，由 lint 强制。
分支名必须来自 `capability.outputs`，不允许从节点属性或 kwargs 泄漏实现身份。

### 3.6 版本盖章

`capabilityRef@range` 在编译期解析成具体版本，盖章写入 process 的 `diagnosticExecution`
扩展元素（`flowable_bridge.py:491-494` 写入，`DiagnosisScheduler.java:26` 与
`ReviewController.java:56` 均从此读取）。`bindings.json` 只保留 worker 侧的派生副本，
两者由同一次 normalize 输出、以同一 hash 绑定。

解析失败即编译失败，不降级到「运行时再试」。

**已盖章的能力版本不可删除，只能标 `deprecated`。** 历史记录的文案按 `resolvedVersion` 渲染
（见 3.10），若该版本的 manifest 被删，老记录就失去文案来源。

但仅靠注册中心保留仍是**策略**，会被清库、迁移、registry 重建绕过，历史文案随即退化为不可知。

**产物必须自包含消息快照。** normalize 时把本图实际引用到的 `declared` code 对应的 messages
子集（通常几 KB）连同 `messageSnapshotVersion` 一起写进 `diagnosticExecution`。这样历史渲染
不依赖注册中心是否还在，registry 侧 `deprecated` 规则降为第二道防线；副产品是离线 ZIP 与
`.bpmn` 也能还原当时文案。

这与现有架构同路——`ReviewController` 本来就是从 extensionElements 读 metadata。

三条配套：

- JSON 内容放 **CDATA**，避免 `&`、`<` 破坏 XML。
- 快照上限 **32 KB，超限直接 fail，不截断**——截断即静默丢文案，比没有更糟。
- 快照自带 `messageSnapshotVersion`，避免改格式后旧部署按新格式解析。

**快照必须确定性序列化，并参与 `diagnosticExecution` 的同一个 hash。**
key 排序、无浮点、无时间戳、无构建号。否则同一张图重复编译得到不同 hash → 每次发布都产生新的
process definition 版本 → 旧实例散落在一堆本该相同的版本上，同时污染「按 `resolvedVersion` 渲染」
与「旧实例跑旧产物」两条已有承诺。

现有 `compile_workflow` 的 `sha256(json.dumps(..., sort_keys=True, ensure_ascii=True))[:12]`
已是这个方向，照它做即可。

快照边界自然收敛：只有 manifest 里 `declared` 的 code 会被引用，未声明异常永远走平台兜底、
不产生引用，所以「只收本图用到的 code」不会漏。

配套校验：`reasonSource = capability` 时，该 code 必须存在于该版本快照内，否则写入即失败。

至此审计链路四环都是物理保证、不靠约定：
**盖版本 → 消息随产物落盘 → 按版本渲染 → 失败内容不被覆盖（uuid 后缀键）**

落盘的 `.diagnosis/manifest.json` 必须带 `contentHash` 与 `derivedFrom`。
`derivedFrom` 记录**签名指纹**（describe 结果 + 类型注解 + signature 字符串），不用文件字节 hash——
否则改一句注释就让编译失败，最终会训练出 `--skip` 的习惯。

一致性校验分两档：manifest 内部自洽始终校验；与注册中心比对只在在线刷新时进行。
离线导出（README 所述「导出 Python 骨架」）必须能脱离后端编译，不因联网校验而失效。

### 3.7 `open` 的约束

`open: true` 表示该能力出口未声明。进 CI 时须双计数：未声明能力数 + 涉及节点数，
否则一个模块声明 `open` 就能隐性豁免几十个节点。

`open` 能力禁止作为 investigation 节点使用。排查节点的出口由 `route_<nodeId>` 与
`selectedRoutes_<nodeId>` 决定（`DiagnosisScheduler.java:117-122`），出口未声明就无法静态确定
分支集合——这里才是真正会被绕过的地方。

> 原拟规则「`open` 不得出现在带 `conditionExpression` 的连线上」恒真无效：
> `flowable_bridge.py:203` 已无条件拒绝条件表达式与默认分支，全图不存在此类连线。

### 3.71 排查节点的双向校验

排查能力的 `outputs.next.enum` 与该节点实际画出的 `diagnosisBranch` 标签要做双向比对，
但两侧处理不同：

- **`drawn ⊆ enum`**（画了但能力声明不了）→ **编译错误**。这是死边，因为路由靠
  `DiagnosisScheduler.java:118-121` 的 branch 相等匹配，声不出来的分支永远走不到。
- **`enum \ drawn ≠ ∅`**（能力能返回但没画）→ **不拦截**，计入 `unreachable-answer` 计数，
  同时打印节点与多余取值。这对应 `DiagnosisScheduler.java:129` 的 `targets.isEmpty() → failure()`，
  是合法的失败路径——「判断走了没有后续分支的方向」本来就应该记录为该思路失败。

区分这两侧是关键：前者是配置错误，后者是业务事实。

### 3.8 opaque 的生命周期边界

`opaque` 只作 `{"type":"opaque","pythonType":"..."}` 占位，永不承载值。

这是契约层唯一兜不住的地方：opaque 值只活在 worker 的 Python 会话内存中，而会话无持久化
（`python_sessions.py` 的 `self.sessions` 是内存字典，`flowable_worker.py` 靠
`pythonSession_<pk>` marker 认领，查不到即抛「会话已丢失」）。因此：

- opaque 值跨过任何人工等待点，重启后即为野指针；
- 影响面不止 opaque：整个 Python 会话重启后都失效，任何依赖会话内对象的节点都会失败。

**处理方式：编译期失败，而非警告。** 判定规则为——opaque 值从产生到消费的路径上跨 suspend 点
（userTask / timer）或跨 session 边界（`scope=isolate`），且未声明
`opaque.revive{capabilityRef, argsFrom}` 时，编译失败。

豁免路径是声明 reviver。注意 reviver 目前不存在，声明它意味着作者必须自己实现
（例如 `machine.reconnect(deviceId)` 从持久化参数重建对象），且 reviver 本身必须无副作用且幂等。

这条规则的代价是严格，但它把「重启后必然野指针」从运行时事故变成编译期错误。
产品语义必须写清楚：**重启后需要人工重做受影响节点，不是无缝续跑**。

### 3.9 retries 由幂等性派生

`retries` 不独立配置，由 `idempotent` 派生，且默认方向是保守的：
未声明 `idempotent` 即视为 `false`，对应 `retries(0)`；只有显式声明 `true` 才允许 bounded retry。

`flowable_worker.py` 现在硬编码的 `.retries(0)` 保留，定位从「写死的值」变为
「fail-safe 默认值」。

### 3.10 失败记录

统一为共享类型，字段全部必填：

`{recordVersion, nodeId, executionId, kind, source, code, reasonSource, reasonParams, value, capabilityId, branch, path, attempt, resolvedVersion, at}`

`recordVersion` 必填，用于区分「旧版本没有这个字段」与「本次显式 unknown」——两者读侧行为相反：
老记录按 `legacy` 只展示已知项，不用当前版本补齐。键不承载语义，值就必须自包含。

`source` 固定五值：`business | route | python | timeout | worker`，写入点硬编码，manifest 不得配置。
用 `route` 而非 `gateway`（同名错误在两处触发，避免误归类）。

`code` 形如 `<domain>.<detail>`，可扩展。`route` 下实际只有两个：

| code | 含义 | 性质 |
|---|---|---|
| `route/no-outlet` | 有出边，但模块返回的 branch 一条都没匹配上 | 配置缺陷，置顶展示 |
| `business/judged-failure` | 业务明确判定失败 | 展示业务结论，不置顶 |

原列入的 `no-selection` 已删除：`ExecutionReviewTask.vue:156` 只在 `paths !== undefined` 时携带
`selectedFlowIds`，`paths` 为空则整条不发送，`[]` 在 UI 上不可达。改为在 review 接口入口校验
`selectedRoutes === []` 直接返回 400，不进入执行。

**裁决：无出边的排查节点是合法终止，不是失败。** 修正 `DiagnosisScheduler.java:129`。

先纠正一个误判：这不是「三方不一致、导出侧少数派」。`README:204` 写的是「**无出口链路**会阻止
导出」，而 `generate.ts:245-252` 的报错条件是「链路没有可达的终止节点」。因为
`generate.ts:233` 已把 `investigation && !outgoing.length` 算作终止节点，这条链路**有**终止节点，
所以两者自洽，真正与二者都冲突的只有 Scheduler。

理由：无出边表示这条思路主动查完、没有产生路由需求；有出边但 branch 不匹配才是「接不住返回值」。
混为一谈会让失败列表充满噪声，用户无法分辨「这条思路排除了」和「图画错了」。

**但导出侧只给 warning，不给 error。** 这是我对两个智能体最终建议的唯一否决点。

它们主张导出时直接报错，理由是「运行时与导出不能两套标准」。但那样反而不自洽：
既然运行时承认无出口是合法终止，导出就没有理由拒绝它。真正该改的是 Scheduler 的 record，
不是导出的 gate。

更实际的理由：改成报错是破坏性变更，昨天还能导出的流程图今天导不出。用户手上已有一批这样的图。

做法：

- 一次性列出全部违规 `nodeId`，不逐个抛；清单可点击定位到节点，不给一串 id 让用户自己搜。
- 文案为「排查节点缺少后续路径」，附「补一条到结论/上升的连线」的迁移提示。
- 导出物带 `exportVersion`。同一套检查跑两个时机、两种呈现：
  - 导入时**不弹框**，只在问题节点挂角标、属性面板给原因。导入的语义是恢复工作，
    弹窗会中断恢复，且用户会学会无脑确认。
  - 导出时弹全量清单——这是用户必须做决定的时刻。
- 发布说明需写明「v2 校验将标记此前可导出的无出口排查节点」。

未知 code 的处理按来源拆成两类，闸门形态保持最简：

- **平台自身 code 缺文案 → 发布即失败，无豁免通道。** 本项目是手工发布，加 key 与发版是同一人，
  缺文案在同一提交里补完即可。给宽限期只会让缺陷带病出厂。
- **外部能力的 `messageKey` 缺 → 不阻断发布。** 这一版本身没坏，是某个第三方能力没跟上。
  保留 fallback（渲染 code）+ warn + 运行期计数，可见性留在指标里。

因此**不设白名单、不设 `expires`、不设「连续两批」状态机**——删掉整套机制，而不是继续加约束。

批次单位用 release tag，不用 commit sha：squash / rebase 会重写 sha，改合并策略计数就抖；
tag 是人为发布动作，语义就是批次。本项目大概率无 tag，此时退化为「发布时主干 tip 的 sha」。

配套硬要求：**tag 发布后不可移动**，须在托管端开标签保护。写在文档里没人守，只有平台强制才生效。

复核后确认：当前固定文案用于无匹配出口；有可选路径时的空选择已经在入口返回 400，
非法 Python 判断值也会单独报错。未来计数和 code 设计应据实际路由场景制定，不把这些入口错误混入。

`reason` 不进协议。文案用 `code` + `reasonSource` 定位：

- `reasonSource` 缺省按 `source` 派生：`route / timeout / worker → platform`，
  `business / python → capability`。声明优先，冲突时编译告警一次并采用声明（见 2.1）。
  但**记录里存的是写入时的实际解析结果，不是派生出的预期值**——`source: python` 下未声明的异常
  本就没有能力侧文案，若记成 `capability` 而实际用了平台兜底，记录与渲染会不一致。
- 平台侧由 code 派生 key（`platform.diagnosis.<code>`）；能力侧由**该 `resolvedVersion` 的
  manifest `messages`** 提供，代入 `reasonParams`。

**文案必须按 `resolvedVersion` 解析，不能用最新版。** 否则插件升级后，同一份历史会显示不同措辞，
等于篡改审计记录。

解析不到时，主文案用 code 的可读兜底加参数，原始 code 与参数放折叠详情。
无 `recordVersion` 的老记录视为 `legacy`，只展示已知字段并标注，不用当前版本补齐。

硬规矩：**展示层与 lint 只读 `source` / `code`，任何程序不得按文案做字符串比较。**

副产品：`unreachable-answer` 的 CI 计数与运行期失败记录共用 `no-outlet` 这个 key。

**以下为待评估的存储方案，不是本轮必须实施的修复。** Scheduler 的数组读改写在同一引擎
命令上下文内执行，本轮并发回归未复现失败记录覆盖。实际复现的是 ReviewController 的
跨命令旧快照覆盖，已通过统一完整复核的命令上下文修复。并行路径依然独立结束，不能为汇总记录
添加会改变业务语义的 join。

若后续选用一条失败一个变量，可考虑以下键格式（尚未实施）：

```
diagnosticFailure_{executionId}_{nodeId | sha256(nodeId)[:16]}_{at_ns}_{rand6}
```

四个分段各有原因，缺一不可：

- `executionId`：并行下同一节点会被多个 token 复用。
- `nodeId`：超过 64 字符时取 `sha256[:16]`。`ACT_RU_VARIABLE.NAME_` 是 VARCHAR(255)，
  节点 id 由用户编辑，一定会写长。
- `at_ns`：回退与复核复用同一 `executionId`，只用前两段会让第二次失败覆盖第一次，
  直接违反「重跑保留此前记录」。时间戳可避免覆盖，但每次生成新键不等于请求幂等。
- `rand6`：防 Windows 时钟刻度内并行撞键。

键**只用于去重**，不用于排序——排序一律用值里的 `at`。

**键不做解析，值里冗余 `nodeId` / `activityId` / `path`。** 变量名可能被引擎改写或加前缀，
靠拆键名还原字段不可靠。`path` 存**快照**不存引用，路径后续会变，失败记录要能还原「当时走到哪」。

**历史读侧已经存在。** ReviewController 的运行时查询用于活动待办，不能据此推断结束后面板无记录。
`backend/server.py` 的执行详情已经读取历史变量，隔离回归确认结束后仍可读取完整记录。
未来若改变变量存储结构，应同步更新这个历史投影，而非给待办接口增加历史回退。

收集用服务端过滤 `variableNameLike('diagnosticFailure_%')`，不拉全量再过滤；
带分页与条数上限，避免长流程把响应撑爆。

**异常按映射分流，不整体改写。** 声明 `errors: [{type, as: "business"}]` 的能力，
只有声明过的异常类型记为业务失败、继续排查；未声明的一律保持基础设施故障（job 失败 → 死信）。
默认方向「不认识的异常当故障」，与 `idempotent` 默认 `false` 同源。

**优先级钉死：声明 > 派生。** 显式 `errors` 命中即按声明走；未命中才用 `idempotent` 判超时是否重试；
两者都未声明即 `timeout → worker` 且 `retries(0)`。

匹配用 `isinstance` / MRO 判断，不按类型名字符串——`TimeoutError` 这类名字在不同库里有不同含义。

整体改为业务失败的后果是：解释器崩溃、import 失败、超时都会伪装成「业务判定失败」，
而死信面板正是靠 job 失败链路工作，会一起失效。

此项改动小、收益明确，可与 P0 同期落地，不必等 P1。

## 4. 接缝（4 个）

### S1 RouteRules：调度语义显式化

不再只做「规则表」，因为表装不下读写时序。采用 **表 + 三个具名原语**：

- `setVar(scope, shadow)` —— 对应现有 `setVariableLocal(name, null)` 的祖先值屏蔽
- `enqueue(front | back)` —— 对应现有深度优先插队
- `recordFailure(path)` —— 对应现有失败记录

原语语义只定义一次，与规则表共同被同一组 fixture 覆盖。

### S2 ConnectionRules：连线规则单源

验证覆盖 81 组诊断类型组合、固定业务预期及普通 BPMN 建模边界。

### S3 契约（即第 3 节）

### S4 ReadModel：只读投影

## 5. 否决项

### 5.1 结构化 BPMN（图即程序）—— 否决

- `compile_workflow` 白名单不接受 `subProcess` / `boundaryEvent`，需先放开白名单。
- `callActivity` 复用模块会断裂：会话键按实例 ID，已证实。
- 失败隔离需为每个节点挂 boundary error，Java 侧代码量不降。
- 编译期自动插网关要保证**任意拓扑**语义正确，把可单测的函数变成不可验证的 XML 生成器。
- 串行模式依赖 `diagnosisOrder` 稳定顺序，而 BPMN 不承诺同层 token 执行次序。

### 5.2 SQLite 状态机替换 Flowable —— 暂缓

四条硬理由：

1. **不可逆副作用盖不住**。「设备动作已发出、事务未 commit」这个窗口无解，恢复即重放，机台重复执行。
   现有实现至少有 deadletter + 人工确认重跑；替换后它变成默认行为。
2. **并发身份要自建**。并行模式下同一节点可能同时挂多个待办，任务主键必须是 `(run, node, token)`。
   token 不天然存在，需自己发号并贯穿回退、历史与幂等键。
3. **重试与死信要自建**。external-worker 的 `fetchAndLock / complete / deadletter / 重试上限`，
   是「动作失败之后怎么办」的完整答案，替换时必须逐项补齐。
4. 需要重新验证原有编译和运行边界；`formatVersion` 数字本身不代表维护了九套兼容实现。

若将来启动，以下四项为必答：`defHash`（改图后旧实例不能按新图跑）、
`effectLog`（动作不得重复执行）、`wait` 快照（改图后待办不得错位）、
逻辑 token 身份（并发多待办与回退的归属）。

### 5.3 dflow DSL —— 否决

与 5.2 同一类，且需维护 DSL ↔ BPMN 双向映射，现有四种导出格式全部重写。

## 7. 边界与残余风险

1. **契约不替代引擎**。`suspend.when` 只是声明「这个能力可以停在等人」，真正的持久化等待仍由
   Flowable userTask 承担。不要读成契约层能自己停。
2. **业务状态需要明确恢复协议**。现已提供 [自动检查点与恢复](RECOVERY.zh-CN.md)，通过对象接口保留原生引用；未声明的对象、未完成动作或不兼容环境仍不能自动恢复。这不等于后文能力契约方案已经实施。
3. **`scope=inherit` 目前无法落地**：它依赖 embedded subProcess，而编译白名单拒绝 subProcess
   （`flowable_bridge.py:238-241`）。要么放开白名单，要么让这条能力显式失败而非静默降级。
4. **展示类能力输出无类型校验**：`chartSvg` 是字符串字段而非 media type，投影层无法校验。
   短期接受，长期应升级。
5. **并发身份未落地**：见 5.2，当前由 Flowable 代管。
6. **golden case 录制需要 `history level = full`**。这是录制器约束，不是产品约束：
   `audit` 级别下系统照常运行，只是回放用例无法录制。应钉进 runtime 配置并做启动自检。
