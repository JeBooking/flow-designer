# 问题清单与核实结果

记录于 2026-10-29，2026-10-30 对照源码及隔离 Flowable 实例复核。保留原编号，区分缺陷、已修复项和待确认的产品能力。

## A. 架构与启动

### A1. Flowable 是否必要 —— 保留，修正职责说明

Flowable 负责流程实例、等待状态、变量、人工待办、执行历史与事务。
并行模式通过 Flowable 网关分叉，各 token 独立继续；只有串行模式使用
`DiagnosisScheduler` 的持久队列，管理思路顺序和成功后的继续／结束选择。
两种模式都使用 Scheduler 记录路径、失败和最终状态，不能概括为“Flowable 只存状态，所有调度都在自己的队列”。

流程等待持久化不等于 Python 业务现场持久化。原先等待期间业务解释器常驻，重启后原生会话不能恢复；本轮通过 C3 的显式检查点协议补齐可恢复工程的持久化与空闲释放。

### A2. 自建等价能力的成本 —— 保留为已排除方案

替换 Flowable 需补齐实例持久化、人工待办、历史、事务、并发、重试及副作用控制。
本轮不更换执行内核，也不实施 ADR 中尚待确认的能力契约设计。

### A3. 本地启动门槛 —— 已降低，无需本机 Maven 的预构建入口

Verification 工作流产出匹配源码提交的 JAR 与校验清单。把两者放入 `flowable-runtime/target/`，
准备 Java 17+、Python 3.9+ 和前端依赖即可启动，无需本机 Maven。启动器校验源码和 JAR 哈希，
统一文本换行，不因检出时间改变而误触发构建。源码变化或产物不匹配时才回到 JDK／Maven 构建。
Python 环境仍由启动器按需创建和安装依赖；仅前端仍可运行 `pnpm dev:frontend`。
详见 [恢复与预构建说明](RECOVERY.zh-CN.md)。

## B. 一致性

### B1. 连线规则有两套实现 —— 已修复

复核时已发现实际差异：前端允许“开始 → 处置动作”，后端编译拒绝。
现统一读取 `src/rules/diagnosis-connections.json`，前端规则和 Python 编译器不再各自维护邻接表。
`generic` 保留普通 BPMN 子流程等建模边界，后端仍只接受支持的诊断执行元素。

`verify-diagnosis-connections.mjs` 对所有诊断类型和开始事件执行 81 组前后端差分，
另用固定业务预期和普通 BPMN 边界断言防止两侧一起误改。

### B2. AGENTS.md 与实际项目不符 —— 已修复

已补充 Python 后端、Java 引擎、诊断调度分工、会话边界、共享连线规则与验证入口。
原有“无服务端 API、无自动验证”的描述已移除。

### B3. 编译签名版本负担 —— 未证实为缺陷

`formatVersion: 9` 参与执行签名，不能据此推断代码维护了九套兼容实现。
应按实际兼容分支和历史实例需求评估，不单独为版本数字启动重构。

## C. 性能与体验

### C1. 轮询全量拉取 —— 已修复

新增按变量修订号读取的引擎历史接口和有界后端投影缓存；客户端使用游标合并新增、更新和删除，
包括先开始、后结束的同一条活动记录。缓存淘汰或后端重启时安全回落完整快照。
状态不变时轮询间隔从 1.5 秒逐步增至 10 秒，提交复核后立即刷新；前端按节点建立索引，
避免每轮对每个节点重复扫描全部历史。待办和死信堆栈不变时不重复传输。

隔离验证中，带 2 MiB 业务值和 600 多个变量的首次响应为 6,374,251 字节，下一次未变化响应为 648 字节。
同时验证变量更新／删除、活动完成、待办变化、结束后历史及后端重启游标重置。

### C2. 刷新后失去监控 —— 已修复

Pinia 持久化最近实例 ID 和最近十个 ID，不保存业务结果。刷新或重建 modeler 自动恢复监控，
也可按 ID 选择已有实例；停止监控不取消执行。切换失败时保留已加载的监控。
后端核对执行签名，画布匹配后才显示高亮；未匹配时仍可使用历史和待办卡片。

### C3. 无自动业务检查点 —— 已实现显式恢复协议与自动持久化

业务模块声明全局无状态，或提供模块状态导出／恢复接口；工厂及原生对象提供对象检查点接口。
worker 在并发调用结束后自动保存原生引用图，在作业确认前缓存响应；恢复相同作业时复用响应，
不再次执行业务动作。人工等待时，安全空闲解释器会释放。后端启动扫描活动实例并恢复缺失协调器。

`verify-execution-recovery.py` 已通过真实后端重启、原待办保持、等待时解释器释放、
原生引用恢复及构造／动作各一次的验证。`verify-session-checkpoints.py` 覆盖并发、
响应重用、源码／依赖环境变化及不完整检查点拒绝恢复。设备会话与 Cooling 示例已接入协议，Cooling 的测量结果、处置状态和进程锁均验证了恢复行为。

边界不隐藏：不支持的对象继续保留活跃会话并显示原因；动作结果不确定、检查点缺失／未完成、
源码或依赖环境变化时拒绝自动恢复，必须先确认现场。无法从展示投影或 `repr` 还原任意设备连接。
恢复协议见 [RECOVERY.zh-CN.md](RECOVERY.zh-CN.md)，不改变显式重查可能重复动作的既有含义。

## D. 工程化

### D1. 验证脚本未接入 CI —— 已接入

新增 `pnpm verify`，自动发现全部 `scripts/verify-*.py` 和 `verify-*.mjs`，
可按 `--group unit` / `--group engine` 执行。原有 21 个脚本加本轮七项回归共 28 个。
真实引擎使用临时数据库与随机端口，日志和退出码统一汇总。

新增 GitHub Actions Verification 工作流，在推送和拉取请求时构建 Java、检查类型、构建前端并执行全部验证。
Windows 参考文件打开器测试使用模拟调用；业务工程不连接真实设备。

部分原验证依赖旧的逐连线路由／任意节点人工判断协议，已经无法通过当前编译。
这些运行用例改用当前合法图；旧示例本身保留，并明确验证缺失分组标签时必须提示迁移。

### D2. 无自动化测试套件 —— 修正表述，已整合现有脚本

没有 `test` 脚本不代表没有自动验证。原脚本已有断言、真实 Python 子进程和真实引擎场景。
本轮复用它们增加统一入口及 CI，没有另引测试框架。

## E. 执行正确性

### E1. 三类失败混用文案 —— 已细分真实路由原因，修正误判

新增版本化失败记录的 ID、executionId、source 和 code。`route/no-outgoing` 表示节点没有后续路径，
`route/unmatched-branch` 表示存在路径但没有匹配判断值；界面按 code 显示中英文原因、判断值和路径，
原始记录保留在折叠详情，旧记录仍使用原有文案。不更改“无出口仍记失败思路”的既有调度语义。

空路径选择已有 HTTP 400 校验，非法 Python 判断值仍进入错误／死信链路，不改成业务路由失败。
串行与并行回归都核对两类 code，并发回归核对版本、执行身份和记录完整性。

### E2. 失败记录实例结束后读不到 —— 误判，无需修复

ReviewController 只在处理活动待办时读取运行时变量；执行面板经 `server.py` 读取历史变量。
隔离验证已确认实例结束后仍可完整读取 `diagnosticFailures` 和复核记录。
不应给已结束的实例重新生成待办，也不需要在待办接口强加历史变量回退。

### E3. 失败记录并发一定覆盖 —— 未复现，不能据读改写直接定性

并行模式并非物理串行。Scheduler 的失败记录在同一个引擎命令上下文内读写，
实际冲突会触发乐观锁和事务回滚。本轮并发回归验证失败记录完整，但不将有限验证等同于无条件安全证明。

### E4. 并发人工复核丢失审计记录 —— 已复现并修复

修复前，在两个顺序对照场景中记录完整；八轮并发场景中有两轮应记录九次复核，实际只保留八条。
全部待办已完成，失败记录完整，缺失的是 `diagnosticReviews`。

根因是 ReviewController 在同一个 Spring 事务中调用了多个独立的 Flowable 命令：
先读取旧数组，后续写回时可能加载更新后的实体版本，导致旧内容以新版本覆盖，乐观锁未必能发现。
现将完整复核操作放入同一个 Flowable 命令上下文，固定读取与写回的实体版本；冲突仍返回 409，由用户刷新重试。
任务完成、回退、动作核验和审计写入共同回滚，不自动重放业务动作。

`verify-review-concurrency.py` 覆盖八个待办并发、结束后历史、无出口失败记录、
动作“不 OK”保持待办及随后“OK”的全部审计，按任务 ID 和记录 ID 检查缺失与重复。
